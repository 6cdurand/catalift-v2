## New bugs / blockers found

### 1. `verifyInviteToken` mis-parses `verify_invitation` RPC result — BLOCKS G, C, D, F in the UI

**Severity:** BLOCKER — the invite flow is the gateway to the entire trainer↔client critical path.

**Repro steps:**
1. Log in as a trainer on staging.
2. Go to `/clients` → `Add Client` → `Create New` → enter an email → `Send Invite`.
3. Copy the generated invite link and open it in an incognito/2nd browser.
4. The `/invite?token=...` page flashes `Verifying Invitation` and then shows `Invalid Invitation`.

**Root cause (observed live):** `supabase.rpc('verify_invitation', { p_token: token })` returns an **array** `[{"email":"...","trainer_name":"...","valid":true}]`. `verifyInviteToken` in `src/features/auth/api/invite.ts` does:

```ts
const row = data as { email: string; trainer_name: string; valid: boolean };
if (row.valid) { ... }
```

`data` is the array, so `row.valid` is `undefined` (falsy) and the function always returns `{ status: "invalid" }`.

**Fix needed:** Handle the array return shape, e.g. `const row = Array.isArray(data) ? data[0] : data;` and test `row?.valid`.

**Evidence:** Direct `curl` to `.../rest/v1/rpc/verify_invitation` with a freshly-created token returned `[]` for a non-existent token and `[{"email":"qa+client-ms2at19a809@catalift.test","trainer_name":"QA Trainer","valid":true}]` for the real token. The `invitations` row was confirmed to exist.

### 2. `/calendar` direct load loses the active flexible one-off

**Severity:** MEDIUM — data loss on direct navigation / 2nd-device open.

**Repro steps:**
1. Trainer assigns a one-off workout to a client.
2. Client signs in and opens `/today` directly — the scheduled session is visible.
3. Client refreshes `/today` — still visible (PASS).
4. Client opens `/calendar` directly (or hard-refreshes from `/today` to `/calendar`) — the calendar grid is empty.

**Root cause:** `useScheduledSessions` (used by `/calendar`) reads `activeProgram` from `useProgramsStore`. The store has no persist middleware and is only hydrated when `useActiveClientProgram` runs (which `/today` uses, but `/calendar` does not). Direct navigation to `/calendar` therefore has an empty store and renders no sessions.

**Regression vs v1 parity:** Likely a regression if v1 calendar showed assigned sessions after a refresh or direct link.

### 3. Trainer Today "Open Workout Builder" still routes to the placeholder `/builder`

**Severity:** MEDIUM UX / navigation bug (same as previous sweep #2).

**Repro steps:**
1. Log in as a trainer.
2. On `/today` (trainer mode) click `Open Workout Builder`.
3. App navigates to `/builder`, which renders `Standalone workout builder is coming soon`.
4. The real working builder is at `/workout/builder`.

This was not fixed by #87/#88.

### 4. Invite page "Sign Up & Accept" does not actually sign the user up

**Severity:** LOW–MEDIUM UX bug (latent until #1 is fixed).

**Observation:** In `src/app/invite/page.tsx`, `handleAcceptInvite` checks `if (user)` and calls `acceptInvite`; otherwise it pushes to `/login`. The button text for an anonymous user is `Sign Up & Accept`, but clicking it loses the invite token and redirects to `/login`. The intended flow (sign up from the invite link and have it accepted automatically) is not implemented.
