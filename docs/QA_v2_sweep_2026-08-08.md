## NEW bugs

### BUG-1 (SEV-1): `getOrCreateConversation` violates `conversations_check1` for ~50% of pairs

The `conversations` table has `check (participant_1 < participant_2)` (lexicographic UUID ordering). `getOrCreateConversation` inserts with `participant_1 = me` and `participant_2 = other`. In this sweep the trainer UUID (`d397...`) is lexicographically greater than the client UUID (`5c12...`), so **every** attempt to open the Messages tab fails:

```
POST https://igagmdkdzjkxrwnyvgqk.supabase.co/rest/v1/conversations
{"code":"23514","details":null,"hint":null,"message":"new row for relation \"conversations\" violates check constraint \"conversations_check1\""}

[MessagesPanel] failed to open conversation: {code: 23514, ...}
```

**Impact:** trainer-client messaging is broken whenever the signed-in user's UUID is greater than the other participant's. Fix: sort the two participant UUIDs before insert, then use the same ordering for lookup.

### BUG-2 (SEV-0): `conversations` RLS does not require a trainer-client connection

`supabase/migrations/20260621233944_00004_messaging_notifications.sql:40-41`:

```sql
create policy conv_insert_member on public.conversations for insert to authenticated
  with check (auth.uid() in (participant_1, participant_2));
```

This only checks that the caller is **one of the two participants**, not that the two users are connected through `trainer_clients`. The UI path `/messages?with=<userId>` triggered by T2 attempted to create a conversation with C. The only reason it did not succeed in this run is the ordering check constraint in BUG-1; an attacker who satisfies the ordering (or directly calls the REST API with `participant_1` set to the lower UUID) can create a conversation and message arbitrary users.

**Impact:** any authenticated user can start a conversation with any other user, bypassing trainer-client isolation. Fix: require `public.are_connected(auth.uid(), other_id)` or an explicit invitation acceptance before a conversation can be created.

### BUG-3 (moderate): Workouts do not feed the `client_sessions` ledger, but the UI says they do

After the client finished a workout, `fetchClients` correctly showed **1 workouts logged** (derived from `public.workouts`), but `ClientPaymentsSection` showed **0 Sessions done** (derived from `public.client_sessions`). The `RateAndAdjustRow` popover tells the user "Logged payments and completed workouts already count automatically." That is false for workouts: the only way to increment `Sessions done` was the manual **+ 1 session** adjustment.

**Impact:** the ledger and the workouts table diverge until a trainer manually corrects the count; the UI text is misleading. Fix: either finish a workout should call `markSessionComplete` (calendar/one-off path), or the help text should not claim workouts count automatically.

### BUG-4 (minor): Client file shows multiple "session"-labelled numbers

The Payments tab displays three session-derived numbers:

- `Sessions done`
- `Paid (sessions)`
- `Outstanding` (rendered as `$0.00` once rate/paid are balanced)

The requirement is that the client file has **one** number labelled "sessions" (the ledger). Overview correctly labels its count "workouts logged", but Payments adds two more session labels around the same data.

### BUG-5 (minor): Program tab has no control when no active program

When no program is assigned, the Program tab renders a read-only empty state with the text "Assign a program from the Builder" but no button or link to do so. The roster card has an `Assign` quick action, but the tab itself has no working control.
